## 1. 30 秒上手

一个插件就是**一个文件夹**,里面至少两个文件:

```
我的插件/
├── plugin.json     ← 清单:我叫什么、要什么权限、什么时候跑
├── main.sh         ← 入口脚本:真正干的活
└── README.md       ← 说明(上架必须,自己用可以不要)
```

`main.sh`:

```sh
#!/system/bin/sh
echo "你好,我是 $(sos-id)"
echo "这次是 $SOS_HOOK 把我叫起来的"
```

打包 → 上架(或者直接放手表里离线装)→ 在 Star OS 应用的「插件中心」里运行。

最短的一条路:**拿 `plugins/com.staros.hello` 改**。它已经是一个完整可跑的插件。

## 2. 插件长什么样

### 2.1 目录结构

```
com.you.myplugin/               ← 目录名建议和 id 一样(不强制)
├── plugin.json                 ← 清单(必须)
├── main.sh                     ← 入口脚本(文件名由 entry 指定,必须)
├── README.md                   ← 说明(上架必须)
├── icon.png                    ← 图标,96×96(可选)
└── res/                        ← 你自己的资源(可选)
    └── tips.txt
```

### 2.2 打包格式 `.sosp`

`.sosp` 就是**改了后缀的 zip**,内容就是上面这些文件的平铺(不要多套一层目录)。
上架由工具打包,不用你手动压。

### 2.3 装到手表之后

```
/data/adb/star_os/plugins/com.you.myplugin/
├── src/      你交上去的内容(只读,别往里写)
├── data/     你的可写目录 ← 要存东西就存这
├── logs/     每次运行的日志
├── meta.conf 元信息(安装时生成)
└── state.conf 启用状态 + 已授权权限
```

## 3. plugin.json 字段

```json
{
  "id": "com.you.myplugin",
  "name": "我的插件",
  "version": "1.0.0",
  "versionCode": 1,
  "author": "你的名字",
  "description": "一句话说明,60 字以内",
  "minApi": 27,
  "entry": "main.sh",
  "permissions": ["notify"],
  "hooks": ["manual"],
  "license": "MIT",
  "homepage": "https://github.com/you/repo"
}
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `id` | ✅ | **反向域名小写**,`^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$`。例:`com.you.myplugin`。装了之后就不能改了(改名等于另一个插件) |
| `name` | ✅ | 显示名,建议 ≤ 10 字。手表屏幕窄,长了会被截 |
| `version` | ✅ | 必须是 `x.y.z`,例:`1.2.0` |
| `versionCode` | ✅ | **≥1 的整数,每次发版必须变大**。设备靠它判断「装的是不是旧版」 |
| `author` | ✅ | 你的名字 / ID |
| `description` | ⭕ | 商店列表里的一句话,≤ 60 字 |
| `minApi` | ⭕ | 默认 27。**不能大于 27**(4100 就是 SDK 27),填大了装不上 |
| `entry` | ✅ | 入口脚本相对路径,一般 `main.sh` |
| `permissions` | ⭕ | 申请的权限数组,默认空。见 [第 4 节](#4-权限) |
| `hooks` | ✅ | 什么时候跑,至少一个。见 [第 5 节](#5-触发时机钩子) |
| `license` | ⭕ | 默认按 MIT 记 |
| `homepage` | ⭕ | 项目地址 |

## 4. 权限

**核心原则:除非你明确声明并且用户明确勾选,否则你拿不到任何系统能力。**

装的时候会弹授权页,逐项勾选,**默认只勾低风险的两项**,高风险默认关闭。
用户可以随时在「插件中心 → 已安装 → 权限」里改。

| 权限 | 风险 | 能做什么 | 对应包装命令 |
|---|---|---|---|
| `ui` | 🟢 低 | 显示插件自己的界面 | — |
| `notify` | 🟢 低 | 弹通知/提示 | `sos-notify` |
| `storage.read` | 🟡 中 | 读内部存储 `/sdcard` 里的文件 | `sos-fs-read` `sos-fs-list` |
| `storage.write` | 🟡 中 | 写内部存储 | `sos-fs-write` |
| `network` | 🟡 中 | 联网 | `sos-http` |
| `settings.read` | 🟡 中 | 读系统设置和系统属性 | `sos-getprop` `sos-settings-get` |
| `settings.write` | 🟡 中 | 改系统设置 | `sos-settings-put` |
| `shell` | 🔴 高 | 以 root 身份执行任意命令 | — |
| `system.prop` | 🔴 高 | 改系统属性(resetprop) | `sos-setprop` |
| `app.install` | 🔴 高 | 安装/卸载应用 | `sos-install-apk` |

### 关于 `shell` 权限:请认真读这一段

**不要随手申请 `shell`。** 它意味着完全控制——改任何文件、装任何东西、把系统搞挂。

而且这里必须实话实说:**在 root 模块里做不到内核级沙箱**。插件一旦拿到
`shell`(真 root),理论上可以绕过 `sos-*` 包装命令直接调底层命令。

真正拦住「坏插件」的是三道闸:

1. **上架审核** —— 工具会对脚本做静态扫描(危险命令、越权使用),源码全程公开在仓库里,任何人都能复查;
2. **禁止二进制** —— 包里不允许出现 ELF / .so / .apk / .dex(见 [第 8 节](#8-审核红线)),因为二进制没法审;
3. **授权页** —— `shell` 会以红色「⚠高风险」展示,默认不勾。

**没申请 `shell` 的插件会被降权执行**(降为 `shell` 用户,uid 2000),
而且 `PATH` 会被收窄到只剩 `sos-*` 包装命令 + 基本系统目录 ——
这一层对「老实写的插件」是硬约束:你没声明权限,`sos-http` 就会直接返回「缺少权限 network」。

> 如果你只申请了 `settings.read`,却直接调 `getprop`,审核会拒绝你并提示
> 「没有声明 settings.read」。**所有系统能力都请走 `sos-*` 包装命令。**

## 5. 触发时机(钩子)

| 钩子 | 什么时候被调用 | 典型用途 |
|---|---|---|
| `install` | 安装完成后立刻跑一次 | 建初始配置、生成默认文件 |
| `boot` | 每次开机(系统启动完成 + 15 秒缓冲后) | 开机自动任务 |
| `manual` | 用户在应用里点「运行」 | 查看信息、手动触发 |
| `uninstall` | 卸载前(然后才删目录) | 清理外部痕迹 |

规则:

- `hooks` 不能为空,至少要有 `manual`;
- **只能跑声明过的钩子**。没声明 `boot`,就算你脚本里写了也不会被开机调用;
- 开机钩子是**并发**跑的,不阻塞开机;单个插件失败或超时,不影响其它插件,也不影响开机;
- 插件被「停用」后,任何钩子都不会跑(手动运行也会被拒)。

## 6. 运行环境

### 环境变量

| 变量 | 含义 |
|---|---|
| `SOS_ID` | 你的插件 id |
| `SOS_PERMS` | 本次实际拿到的权限,逗号分隔(可能是空字符串) |
| `SOS_HOOK` | 本次是哪个钩子在跑:`install` / `boot` / `manual` / `uninstall` |
| `SOS_DIR` | 插件目录 `/data/adb/star_os/plugins/<id>` |
| `SOS_SRC` | 你的只读内容目录 `<SOS_DIR>/src` |
| `SOS_DATA` | **你的可写目录** `<SOS_DIR>/data` |
| `SOS_MODDIR` | 模块目录 `/data/adb/modules/zz_star_os` |
| `SOS_PLUGIN_HOME` | 所有插件的根目录 |
| `SOS_API` | 插件 API 版本,当前 `1` |

### 工作目录与 PATH

- **cwd 就是 `$SOS_DATA`** —— 相对路径写入都落在这里;
- `PATH` 被收窄成 `<所有插件的根目录>/.bin:/system/bin:/system/xbin`,
  开头那个目录里是注入的 `sos-*` 包装命令;
- 别指望 `bash`、`python`、`awk`(部分 busybox 版本有)这类东西一定存在。

### 身份

| 情况 | 以什么身份跑 |
|---|---|
| 已授权 `shell` | **root** |
| 没授权 `shell` | 尽量降权到 `shell`(uid 2000);本机降不了权时以 root 跑,并在日志里明确标注 |

想确认自己是以什么身份跑的,看日志头部的「身份:」那一行。

### 输出与日志

- `echo` 到 stdout / stderr 的内容**全部会写进日志**;
- 日志文件:`<SOS_DIR>/logs/<时间戳>-<钩子>.log`;
- 在应用里点「日志」能看到最近一次;也可以直接 `cat` 文件;
- **不要往 stdout 打大量内容**(比如循环里 print),日志会长到没法看。

### 超时与失败

- 单个钩子的执行有上限(执行器侧控制),**跑不完会被终止**;
- 退出码非 0 只代表「这次失败」,不会影响系统,也不会阻止其它插件跑;
- 别写 `while true` 这种死循环。

## 7. sos-* API 参考

这些都是**注入的命令**,直接当普通命令调用即可。权限不足时会以退出码 **3** 失败,
并在 stderr 打一行说明。

### 7.1 不需要权限

| 命令 | 说明 |
|---|---|
| `sos-id` | 打印自己的插件 id |
| `sos-dir` | 打印自己的插件目录 |
| `sos-perms` | 打印本次拿到的权限(逗号分隔) |
| `sos-api` | 打印插件 API 版本 |
| `sos-log <文本>` | 往日志里写一行 |

```sh
echo "我拿到的是 [$(sos-perms)]"
sos-log "开始处理"
```

### 7.2 文件(需 `storage.read` / `storage.write`)

| 命令 | 说明 |
|---|---|
| `sos-fs-read <路径> [输出文件]` | 读文件。给了输出文件就写进去,否则打到 stdout |
| `sos-fs-list <目录>` | 列目录(等价 `ls -la`) |
| `sos-fs-write <路径>` | 从 **stdin** 读内容写进文件 |

**只能操作内部存储**(`/sdcard`、`/data/media/0`、`/storage/emulated/0`),
越界会以退出码 4 失败。

```sh
# 读
sos-fs-read /sdcard/StarOS/notes.txt
# 写(注意是从 stdin 读)
echo "今天的记录" | sos-fs-write /sdcard/StarOS/log/$(date '+%m%d').txt
```

### 7.3 网络(需 `network`)

| 命令 | 说明 |
|---|---|
| `sos-http <url> [输出文件]` | 只支持 http/https。给了输出文件就存文件,否则打到 stdout |

```sh
sos-http "https://example.com/data.txt" "$SOS_DATA/cache.txt"
```

### 7.4 提示(需 `notify`)

| 命令 | 说明 |
|---|---|
| `sos-notify <标题> <内容>` | 弹一条系统通知 |

```sh
sos-notify "Star OS" "电量已充满"
```

### 7.5 系统设置与属性

| 命令 | 需要 | 说明 |
|---|---|---|
| `sos-settings-get <命名空间> <键>` | `settings.read` | 读系统设置,如 `sos-settings-get system screen_brightness` |
| `sos-settings-put <命名空间> <键> <值>` | `settings.write` | 改系统设置 |
| `sos-getprop <属性名>` | `settings.read` | 读系统属性 |
| `sos-setprop <属性名> <值>` | `system.prop` | 改系统属性(内部走 resetprop) |

```sh
echo "亮度 = $(sos-settings-get system screen_brightness)"
echo "机型 = $(sos-getprop ro.product.model)"
```

### 7.6 装应用(需 `app.install`)

| 命令 | 说明 |
|---|---|
| `sos-install-apk <apk路径>` | `pm install -r -d` |

### 7.7 退出码约定

| 退出码 | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 用法/参数错 |
| 3 | **权限不足** |
| 4 | 路径越界(不属于内部存储 / 不是 http) |
| 5 | 文件不存在、写入失败、依赖命令缺失 |

建议在你自己的脚本里也用 0 表示成功,别用其它数字表示「正常但没事」。

## 8. 审核红线

上架前会**逐行静态扫描**,命中下面任何一条就是拒绝,没有例外。

### 8.1 绝对禁止(出现即拒)

| 规则 | 例子 |
|---|---|
| 禁止二进制文件 | 包里出现 `.so` / `.apk` / `.dex` / `.jar`,或任何 ELF(改后缀也不行) |
| 禁止清空/删除系统关键目录 | `rm -rf /`、`rm -rf /system`、`rm -rf /data` |
| 禁止格式化 / 刷写 | `mkfs`、`dd of=/dev/...`、`fastboot`、`flash_image` |
| 禁止内核模块 | `insmod`、`modprobe` |
| 禁止挂载 | `mount`、`umount` |
| 禁止改 SELinux | `setenforce`、`setsebool` |
| 禁止直接操作应用 | `pm uninstall/disable/clear`、`am force-stop` |
| 禁止直接写 /system | `> /system/...` |
| 禁止自己提权 | `su -c ...`、`su 0 ...` |
| 禁止装模块 | `magisk --install-module` |
| 禁止重启关机 | `reboot`、`shutdown` |
| 禁止改防火墙 | `iptables` |
| 禁止 fork 炸弹 | `:(){ :|:& };:` |

### 8.2 用了必须声明对应权限

| 你写了 | 就得声明 |
|---|---|
| `getprop` / `sos-getprop` | `settings.read` |
| `setprop` / `resetprop` / `sos-setprop` | `system.prop` |
| `settings put` / `sos-settings-put` | `settings.write` |
| `settings get` / `sos-settings-get` | `settings.read` |
| `curl` / `wget` / `sos-http` | `network` |
| `pm install` / `sos-install-apk` | `app.install` |
| `sos-fs-read` / `sos-fs-list` | `storage.read` |
| `sos-fs-write` | `storage.write` |

> 记忆法:**想知道系统任何东西 → `settings.read`;想改任何东西 →
> 对应的 write 权限;想上网 → `network`。走 `sos-*` 包装命令就绝不会错。**

### 8.3 会提醒但不禁

`eval`、`base64 -d`(可能藏东西)、`while true`、超长 `sleep`、
`nohup`/`setsid`(脱离进程)、单行超过 400 字符(常用来藏东西)、
description 过长、没写 license。

### 8.4 其他硬性要求

- 必须有 `README.md`(写清:做什么、用哪些权限、数据存哪);
- 入口脚本第一行必须是 `#!/system/bin/sh`;
- 包体 ≤ 1 MB,解包后 ≤ 20 MB,文件数 ≤ 200;
- `versionCode` 每次发版必须递增。

## 9. 上架流程

```
你写好插件
   ↓
用「Star OS 插件工具」(Windows) 选插件目录
   ↓
工具做审核(就是第 8 节那套规则),不合格会直接告诉你哪一行有问题
   ↓
审核通过 → 工具打包 .sosp + 算 sha256 + 更新 index.json + 推到仓库
   ↓
所有装了 Star OS 1.5+ 的用户,在「插件中心 → 商店」里就能看到并安装
```

投稿也可以直接往仓库提 PR / issue,作者用工具走同一条审核流程。

**商店索引** `index.json` 长这样(由工具自动维护,不用手写):

```json
{
  "schema": 1,
  "updated": "2026-10-05T09:05:21Z",
  "plugins": [
    {
      "id": "com.staros.hello",
      "name": "你好插件",
      "version": "1.0.0",
      "versionCode": 1,
      "author": "星",
      "description": "最小示例",
      "permissions": [],
      "hooks": ["install", "manual"],
      "file": "dist/com.staros.hello-1.0.0.sosp",
      "size": 2115,
      "sha256": "bb61cf17…"
    }
  ]
}
```

设备端下载后**必须先校验 sha256**,对不上直接丢弃 —— 这一步是强制的,绕不过。

## 10. 不上架:本地自用

不打算公开的插件不用走审核,两条路:

1. **应用内离线安装**:把 `.sosp` 放到手表的
   内部存储 `/StarOS/plugins/` 目录,然后在「插件中心 → 本地」里点安装;
2. **命令行**:`su -c "sh /data/adb/modules/zz_star_os/plugin_exec.sh install /sdcard/xxx.sosp"`。

本地装的插件和商店装的走完全一样的权限检查,不会因为「本地」就松。

## 11. 调试

### 在手表上看日志

- 应用里:插件中心 → 已安装 → 日志;
- 命令行:`su -c "sh /data/adb/modules/zz_star_os/plugin_exec.sh log com.you.myplugin 100"`。

日志头部会写明**插件 id / 钩子 / 时间 / 执行身份 / 权限 / 入口**,
排查问题先看这几行。

### 手动跑一次

```sh
su -c "sh /data/adb/modules/zz_star_os/plugin_exec.sh run com.you.myplugin manual"
```

### 看插件状态

```sh
su -c "sh /data/adb/modules/zz_star_os/plugin_exec.sh info com.you.myplugin"
```

会打印 `meta.conf`(元信息)和 `state.conf`(启用状态 + 已授权权限)。

### 在电脑上先跑一遍脚本逻辑

如果只是纯 shell 逻辑(不依赖 Android 专有命令),可以在电脑上
`sh main.sh` 跑,但记得:

- `sos-*` 命令在电脑上没有,得自己造桩;
- 别依赖 `/proc`、`getprop` 这些。

### 常见失败原因

| 现象 | 原因 |
|---|---|
| 日志里「身份: root(无法降权)」 | 没授权 `shell`,而本机降权不可用。给 `shell` 或忽略 |
| `sos-*` 返回退出码 3 | 权限不足。去应用里勾上对应权限 |
| 装不上,提示「未知权限」 | 权限名拼错了,或用了表里没有的权限 |
| 装不上,提示「未知钩子」 | `hooks` 里写了表外的值 |
| 装不上,提示「minApi 高于本机」 | `minApi` 填 > 27 |
| 开机没被跑到 | `hooks` 里没写 `boot`,或插件被停用了 |
| 「插件未声明 xxx 钩子」 | 想跑没声明的钩子。钩子必须提前声明 |

## 12. 示例逐行讲解

仓库里有三个可直接参考的插件:

### `com.staros.hello` —— 最小示例(零权限)

```sh
#!/system/bin/sh                              ← 必须这一行
echo "你好,这里是 $(sos-id)"                  ← 无权限命令
echo "触发钩子 : $SOS_HOOK"                    ← 环境变量
echo "我拿到的权限:[$(sos-perms)]"
echo "ran at $(date '+%s')" >> "$SOS_DATA/hello.log"   ← 写自己的数据目录
```

要点:
- 没申请任何权限,所以 `sos-getprop` 这类命令**不能用**(会返回权限不足);
- `$SOS_DATA` 是唯一被保证可写的地方,临时文件也放这儿;
- `plugin.json` 里 `hooks` 是 `["install","manual"]` —— 装完自动跑一次,之后可以手动跑。

### `com.staros.sysinfo` —— 只读插件(一个中风险权限)

```json
"permissions": ["settings.read"],
"hooks": ["manual"]
```

```sh
echo "型号 : $(sos-getprop ro.product.model)"   ← 走包装命令读属性
head -3 /proc/meminfo                            ← 纯查看命令不需要权限
```

要点:
- 想读属性 → 声明 `settings.read` 并用 `sos-getprop`;
  直接写 `getprop` 会被审核拒(提示没声明权限);
- `/proc`、`df` 这类**纯查看、改不动任何东西**的命令不需要权限,可以直接用。

### 写一个自己的插件,推荐顺序

1. 复制 `com.staros.hello` 到你自己的目录;
2. 改 `plugin.json` 的 `id` / `name` / `description`;
3. 按需要往 `permissions` 里加权限(**按最小够用原则**,能不加就不加);
4. 写 `main.sh`。**先只 echo,确认能跑通**;
5. 再逐步加功能,每加一个系统能力就回去核对权限表;
6. 用工具审核 → 打包 → 上架。

## 13. 常见问题

**Q:能不能带自己的二进制 / 编译好的程序?**
不能。包里禁止任何二进制文件(ELF / .so / .apk / .dex / .jar),改后缀也会被识别出来。
原因很直接:二进制没法审核,而「能审」是这套插件系统能存在的前提。
纯 shell + busybox 能做的事其实不少,实在要复杂逻辑,用 `sos-*` 组合。

**Q:能不能在插件里读别的插件的数据?**
不行,也不该那么设计。每个插件有自己的 `data/`,互相隔离。
插件之间要通信,请通过内部存储或系统设置中转。

**Q:插件能改开机动画 / 主题 / 字体吗?**
这些属于系统文件修改,需要 `shell` 权限,而且改错会导致开不了机。
上架审核对这类改动会非常严格。**不建议**插件碰这些,模块本身已经做了。

**Q:我申请了权限但用户在授权页没勾,会怎样?**
插件照常能装、能跑,但调用对应 `sos-*` 命令时返回退出码 3。
你的脚本应该**优雅处理**,而不是当作致命错误直接退出。

**Q:改了什么情况要提 versionCode?**
任何一次对外发布都要。设备靠 `versionCode` 判断新旧,
不提的话用户装不上新版(会被当成同版本)。

**Q:`id` 能不能改?**
不建议。`id` 变了就是另一个插件,用户得卸载重装,数据也会丢。

**Q:能申请 `shell` 吗?**
能,但要接受:它会在授权页显示为红色高风险、默认不勾,
审核也会重点盯你源码。**先想想有没有更小的权限组合能做到。**
