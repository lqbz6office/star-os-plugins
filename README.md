# Star OS 插件商店

给 [Star OS](https://github.com/lqbz6office/star-os-assets)(小天才手表 4100 / Android 8.1 的 Magisk 模块)
用的插件仓库。装了 **Star OS 1.5 及以上**的模块后,打开「Star OS」应用 → 右上角「插件」→「商店」,
就能直接看到并安装这里的插件。

---

## 目录里有什么

| 路径 | 说明 |
|---|---|
| `index.json` | **商店索引**。设备拉这个文件拿插件列表、权限、sha256 |
| `dist/*.sosp` | 打包好的插件包(设备下载的就是这些) |
| `plugins/<id>/` | 插件源码。商店里每个插件在这里都能查到原文 |
| `docs/插件开发文档.md` | **开发者必读**:怎么写插件、权限表、API、审核红线 |
| `submissions/` | 投稿区(走 PR 或 issue) |
| `feedback/` | 问题反馈说明 |
| `.github/ISSUE_TEMPLATE/` | 投稿与反馈的表单模板 |

---

## 给使用者

1. 手表上打开 **Star OS** 应用 → 右上角 **插件 ›**
2. 切到 **商店**,点开一个插件看详情(会列出它申请的权限)
3. 点「安装」,装完会弹**授权页** —— 逐项勾选,不勾的权限插件就拿不到
4. 到 **已安装** 里点「运行」看效果,点「日志」看输出,点「权限」随时改授权

不想联网也行:把 `.sosp` 放到手表内部存储 `/StarOS/plugins/`,在 **本地** 分区里装。

### 关于权限,请记住这两条

- **默认只勾低风险的两项**(`ui` / `notify`)。其余权限,尤其是 `shell`,默认是关的,要你自己去勾。
- `shell` = 完全控制。给出去之前请想清楚。

### 现有插件

| 插件 | 权限 | 说明 |
|---|---|---|
| **你好插件** `com.staros.hello` | 无 | 最小示例,确认插件系统通不通 |
| **系统信息** `com.staros.sysinfo` | `settings.read` | 只读:机型、版本、内存、存储 |
| **每日一句** `com.staros.dailytip` | `notify` | 每次开机弹一条小贴士 |

## 给开发者

完整规范见 **[docs/插件开发文档.md](docs/插件开发文档.md)**。最要紧的几条先说在这里:

- 插件就是一个文件夹:`plugin.json`(清单) + `main.sh`(入口) + `README.md`(说明)
- **禁止携带任何二进制**(ELF / `.so` / `.apk` / `.dex` / `.jar`)。二进制没法审,这是上架的前提
- **用了系统能力就必须声明对应权限**,并且走注入的 `sos-*` 包装命令
- 想要系统能力却直接调 `getprop` / `settings` / `curl`,审核会拒
- 高风险权限(`shell` / `system.prop` / `app.install`)会在授权页显示红色警告

最快的上手方式:复制 `plugins/com.staros.hello` 改。它已经是完整可跑的插件。

## 怎么上架

```
写插件 → 用「Star OS 插件工具」(Windows) 打开插件目录
       → 工具按 docs 里的规则做静态审核(不合格会指出哪一行)
       → 通过后打包 .sosp + 算 sha256 + 更新 index.json + 推到这个仓库
       → 所有用户在新版应用的商店里就能看到
```

也可以直接给本仓库提 **PR / issue**(有对应模板),作者用同一套工具审核后合入。
投稿放 `submissions/<你的插件id>/`。

## 版本与兼容

- 最低要求:Star OS 模块 **1.5**、插件 API **v1**
- 目标机型:**4100(SDK 27 / Android 8.1)**
  (1.5 起模块不再支持 5100,所以插件也只面向 4100)
- 插件自己的 `minApi` 填大于 27 会被拒 —— 填了也装不上

## 安全模型(实话实说)

这套插件系统**不是内核级沙箱**,在 root 模块里也做不到。真正起作用的是四层:

1. **包装层强制** —— 没声明权限,`sos-*` 命令直接以退出码 3 拒绝;
   没申请 `shell` 的插件会被降权执行(uid 2000)且 `PATH` 被收窄
2. **上架审核** —— 静态扫描危险命令与越权使用,**源码全程公开在本仓库**,谁都能复查
3. **禁止二进制** —— 让「审源码」这件事在物理上成立
4. **用户逐项授权** —— 高风险权限默认关闭,授权页红色标注

`shell` 一旦授权就是真 root,绕得过包装命令 —— 这一点我们不假装能拦住,
所以对申请 `shell` 的插件,审核和源码公开是唯一也是最有效的手段。
